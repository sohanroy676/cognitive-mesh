# System Patterns

## Naming conventions
- Package `cognitive_mesh` (import), `cognitive-mesh` (distribution and console script).
- Env vars: `COGMESH_` prefix, except the conventional `GROQ_API_KEY`.
- Tests: `tests/test_*.py`.

## Folder structure logic
- `src/` layout: all product code in `src/cognitive_mesh/`; tests in `tests/`.
- Significant decisions go in `docs/adr/` (0002-0004 cover tooling and config, 0005 ingestion, 0006 dependency graph, 0007 JS/TS, 0008 visualization).

## Common patterns used in this project
- Configuration is read only through `cognitive_mesh.config.load_settings()`; never `os.environ` directly elsewhere.
- Secrets are `SecretStr`; never log or print them, and keep them out of error messages.
- Config failures raise `ConfigError`; the CLI maps them to exit code 2 (0 = ok).
- Tests run via an autouse fixture (`tests/conftest.py`) that clears config env vars and uses an empty temp cwd, so a real `.env` never leaks in.

- Ingestion (`cognitive_mesh.ingestion`, ADR-0005): per-file problems are `Diagnostic`s, never exceptions; only a bad root raises `IngestionError` (CLI exit 3). Ingested content is data: never imported, executed or put in diagnostics (not even parser error text). All file reads go through `ingest._read_bytes`; tests spy on it to prove sensitive files are never opened.
- Every ingested record carries a `SourceRef` (relative POSIX path + sha256 of the original bytes) and the rule that classified it. Secrets found in content are replaced by `[REDACTED:<rule>]`; the sha256 still refers to the original bytes.
- Test fixtures: benign app committed in `tests/fixtures/sample_app/`; hostile files (secrets, binaries, malformed) are created in `tmp_path` at test time, and fake secrets are assembled at runtime. Keep parametrize ids short (huge inputs in ids break pytest on Windows).

- Changelog: `CHANGELOG.md` is generated by git-cliff (`cliff.toml`), never hand-edited. Regenerate as the very last commit of a branch (`chore(changelog): regenerate`); any later non-merge, non-`chore(changelog)` commit makes it stale and CI fails. Use `fix`/`feat`/`docs`/`build`/`ci` for things that belong in it; `chore(deps)` is skipped by design.
- Versioning: never hardcode a version. The version is the latest `v*` git tag (hatch-vcs); a release is made by tagging. `__version__` is read from installed metadata, so after tagging re-run `uv sync` to refresh an editable install.

## Things to avoid
- Hardcoding credentials or committing `.env` files (only `.env.example`, placeholders only).
- Documenting commands that have not been run successfully.
- Marking a roadmap version done before its verification criteria pass.
- Dependency graph (`cognitive_mesh.graph`, ADR-0006): `A -> B` always means "A depends on / imports B". Every `Edge` has >=1 `Evidence` (SourceRef + line + rule + cited text); the model rejects none. Anything not resolvable becomes an `unresolved` node plus a diagnostic, never a guessed edge; imports are never linked to packages by name. Builders (`graph/builders.py`) are pure over `IngestionResult` and never touch the disk. NetworkX stays private to `graph/graph.py`; public API returns frozen pydantic models; outputs are sorted for determinism. Only `GraphError` (unknown node id) is raised (CLI exit 4).
- JS/TS and dynamic imports (ADR-0007): tree-sitter is imported only in `graph/js_parse.py`, which returns plain `JsImport` records; matching is on syntax nodes (never regex/text) so comments, strings, template text, regex and JSX text cannot create edges; the walk is iterative; nodes in ERROR subtrees are skipped and reported as a `parse_error` warning. A dynamic import whose target is not a plain literal becomes `unresolved:dynamic:<path>:<line>` plus a `computed_import` warning, never a guessed edge. Bare/aliased JS specifiers stay `unresolved:import:js:<pkg>` (the npm `candidate_package` is a hint only). `.js` is never remapped to `.ts`.
- Test fixtures: `tests/fixtures/js_app/` holds the JS/TS fixture (decoy imports in comments/strings/regex/JSX that must never become edges). Do not write big files in tests without checking Windows speed: opening a fresh 880 KB file took ~23 s here.
- Visualization (`graph/view.py`, `render_mermaid.py`, `render_html.py`, ADR-0008): renderers are pure functions of a `GraphView` made by `build_view`, which only selects from the graph (never adds or rewrites). Graph text is untrusted: HTML uses `esc()` (visible escapes, HTML escape, `&#N;`) in text nodes only; ids/classes are generated and CSS is constant; Mermaid never uses graph text as an identifier and entity-encodes everything outside a safe set. Output is ASCII/LF with no absolute paths or timestamps. Truncation is always announced. Any new renderer needs hostile-name tests (see `tests/test_graph_render.py`) and must leave text/`--json` output unchanged. In `graph/__init__.py` the names `render_html`/`render_mermaid` are the functions, not the modules (patch via `sys.modules` in tests).
- Test fixtures: `tests/fixtures/expected/` holds golden outputs (`dep_app.mmd`, `js_app.mmd`, `dep_app.txt`); regenerate only after reviewing the diff.
- Test fixtures: `tests/fixtures/dep_app/` is the graph fixture (cycle a<->b, undeclared and declared imports, `-r`/URL requirement lines); `tests/fixtures/` is excluded from mypy.
