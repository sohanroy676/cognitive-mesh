# Feature notes

What each later version added, what it does and, in each paragraph, what it does not do or has not been run
against. These notes moved out of the README; the version-by-version record is in [STATUS.md](STATUS.md) and
every command is in [COMMANDS.md](COMMANDS.md).

A catalog (v1.8.0, [ADR-0038](adr/0038-model-catalog-and-call-records.md); example in
[model-catalog.example.toml](model-catalog.example.toml)) lists models behind an OpenAI-compatible
endpoint or Ollama. It never holds a key, only the name of the variable that does. A remote entry needs
`COGMESH_ALLOW_REMOTE_CONTENT=true`, and a free tier whose `data_use` you declared `may_train` or `unknown`
also needs `COGMESH_ALLOW_TRAINING_USE=true`; `data_use` is your statement, not checked. Each model call is
recorded with the run (latency, tokens when the provider reports them, result kind; never prompt or reply
text): `cognitive-mesh models stats --db FILE` shows counts per model, role and task type and does not rank
models. Request shapes for Gemini, OpenRouter and Mistral are from their documentation and have not been run
against the real services.

Decisions (v1.9.0, [ADR-0039](adr/0039-decision-records.md)) are records of what was decided, the options, the reasoning and the evidence cited: `cognitive-mesh decisions record` stores one (a cited file keeps its hash), `decisions trace --pr ORG/REPO#N` goes from a pull request back to the decisions and their evidence, and a status (`stale` when a cited file changed, `validated` only by a recorded outcome for the current code) is computed each time. Reasoning is what its author wrote, never evidence for itself; nothing writes a decision on its own yet.

Conducted tasks (v1.10.0, [ADR-0040](adr/0040-orchestrator-model.md)): `cognitive-mesh task REQUEST --conduct --conductor ENTRY --catalog FILE ...` lets a conductor model draft the plan and choose a catalog model for each model step. Its plan is data: it is validated before anything runs (an unusable plan exits 22 and nothing runs), every assignment shows a count-based evidence label (`recorded` from 20 calls with a known outcome, otherwise `insufficient_evidence`; nothing is called better), a rate-limited or unavailable model hands over to the next eligible catalog entries, and the plan, each assignment and every call are recorded, with the conductor's reasons stored as `model_unverified` decisions. `--explore-rate` is off by default. Only a scratch stub server has conducted a task so far; no real model has.

Cross-project impact (v1.11.0, [ADR-0041](adr/0041-cross-project-impact-analysis.md)): `cognitive-mesh workspace impact PROJECT --target T --workspace FILE` lists every other workspace project and location that depends on a file, route, table, environment variable, package or exported name of the current project, with the evidence on both sides; what may depend on it but cannot be resolved (a computed URL, a whole-module import) is listed apart as `unknown`. `workspace contract-diff PROJECT [--base REF]` compares the project's working tree with a git ref (a read-only `git archive`; nothing is checked out or written) and labels each difference that other projects use as `breaking`, `compatible` or `unknown`, where `unknown` is never counted as a pass. `run` and `task` accept `--workspace FILE --project NAME`, so the `dependents_of` capability and the model-backed `reader` role can see the other projects, read-only (only the named project may ever be written). Only the contracts the extractors can read are compared (routes, typed columns, JSON Schema properties, configuration names, package version and exports); request and response bodies are not. The reader has not been run with a real model.

Showing improvement (v1.13.0, [ADR-0043](adr/0043-showing-improvement.md)): `cognitive-mesh eval run TASKSET.toml --out DIR --model ID --catalog FILE [--repeats N] [--allow-unisolated-checks]` runs each task of a small task set through the change pipeline twice, memory off and memory on, with the same model; the memory-on arm sees only its own earlier tasks. `eval report DIR [--json]` prints counts for both arms, lists every aborted or unfinished item and says `too few paired tasks to conclude anything` below 20 pairs. It shows nothing about improvement at this scale: it is the tool for measuring it later. Checks run with your privileges and are not isolated.

Small changes (v1.12.0, [ADR-0042](adr/0042-small-change-agent.md)): `cognitive-mesh change propose REQUEST --root DIR --workspace FILE --project NAME --db FILE --outcomes FILE --worktrees DIR --file PATH ...` asks a coder model for a small unified diff of the current project only (default limit 3 files and 100 changed lines). The diff is judged by our own parser first (plain relative paths inside the project, no renames, deletions, binaries, modes or secrets files, nothing in another workspace project), applied in a separate git worktree on a new `cogmesh/change-ID` branch (the checked-out branch and working tree are never touched, repository hooks never run), and held against the v1.11.0 contract diff: a change that breaks something another project uses is refused and sent back, up to two revisions. The project's check command is the one a person declared with `workspace set-check PROJECT -- COMMAND ARG...` (never read from the repository); it runs only with `--allow-unisolated-checks`, in a reduced environment with a timeout and a process-tree kill, and its exit code is stored as a `check` outcome labelled `env_only`: this is **not** isolation, the command runs with your rights and a raw socket still works. `change approve ID --by NAME` records a person's approval of exactly one commit and diff; `change pr ID --root DIR` then pushes the branch (never forced) and opens a pull request with a `GITHUB_TOKEN` and `COGMESH_ALLOW_REMOTE_CONTENT=true`. Nothing is pushed without those two steps and nothing is merged by the tool. The diff, its summary and its reasoning are a model's words (`model_unverified`); only a recorded check validates, and only for that command. No real model has written a diff and no pull request has been opened on github.com yet.
